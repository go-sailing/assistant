## 1. 背景与目标

### 1.1 背景

v0.4.0 完成农历/法定工作日历、方案卡与账号体系后，助手在单轮对话内的体验已经顺畅，但**跨多轮、跨会话的"记性"问题**开始暴露，同时真实使用中沉淀了 5 个明确的体验瑕疵。v0.5.0 需求共 7 项，分为两组：

**助手记忆能力缺失（新增 2 项）**

1. **长对话必然"失忆"**：当前每轮对话只取最近 20 条消息（`CHAT_HISTORY_LIMIT=20`）注入模型，更早的对话被硬截断。用户与助手连续安排一周工作后，助手不再记得更早前提（"还是按上次说的，站会改到 9 点半"无法解析）；而一次性放开历史又会超出模型上下文窗口。需要在超限时**自动压缩**旧上下文，在有限窗口内保留尽量多的有效信息；
2. **换会话即"人走茶凉"**：助手对用户的长期偏好、长期事项零记忆。用户需要一个明确的"**归档聊天记录**"动作：归档时从对话中提炼并保存**长期记忆**，之后新会话也能用上；记忆必须由用户掌控——可查看、可删除。

**体验优化（5 项）**

3. **全天日程制造无意义冲突**：全天日程（如"国庆节""出差全天"）跨 00:00–次日 00:00，与当天任何定时日程都"时段相交"，系统会弱化提示冲突，但全天安排本就不排斥当天再排定时日程，提示纯属打扰；
4. **个人信息页入口冗余**：个人信息页（`/me`）中的"清除聊天记录"与助手页更多菜单、系统设置页重复，应从个人信息页移除；
5. **设置页"修改密码"冗余**：修改密码在个人信息页已有入口，设置页的"账号安全"分组仅这一项，应删除该分组；
6. **抽屉退出按钮易误触且冗余**：左侧抽屉左下方常驻"退出"按钮，退出登录在个人信息页、系统设置页危险区均有入口，抽屉按钮应移除；
7. **聊天里改日程刷出一长串日程卡片**：对话中修改一个日程时，助手为定位对象先调用日程查询，查询结果（可能是当天/几天内的全部日程）被当作卡片整块写进聊天记录，日程一多就是长长一串卡片，干扰阅读。

7 项需求编号与分组：

| 分组 | 编号 | 需求 |
| --- | --- | --- |
| 助手记忆（新增） | CTX-01 | LLM 聊天上下文自动压缩：上下文超限时自动压缩 |
| 助手记忆（新增） | MEM-01 | 归档聊天记录：归档时提取并保存长期记忆，支持查看与删除 |
| 日程优化 | EVT-01 | 全天日程不进行时间冲突提醒 |
| 入口收敛 | UI-01 | 删除个人信息页"清除聊天记录"项 |
| 入口收敛 | UI-02 | 删除设置页"修改密码"项（账号安全分组） |
| 入口收敛 | UI-03 | 删除左侧抽屉左下方"退出"按钮 |
| 聊天体验 | CHAT-01 | 优化聊天中修改日程时展示一大串日程卡片的问题 |

### 1.2 产品目标（v0.5.0）

- **核心目标**：
  1. 助手在长对话中不因历史条数增加而丢失早期有效信息，压缩过程对用户零打扰、零操作；
  2. 用户通过"归档"主动沉淀长期记忆，新会话能延续对用户的了解；记忆完全可见、可删、可控；
  3. 全天日程彻底退出冲突提醒，冲突提示只保留真正有意义的"定时时段重叠"；
  4. 完成账号/聊天相关入口去冗，每个危险/高频动作只有恰当的 1~2 个入口；
  5. 聊天记录只呈现"用户该看的内容"：过程性数据查询不落地为卡片，写操作只展示被改动的对象。
- **成功假设**：
  1. 长对话（>20 轮）用户中，"助手不记得前面说过的事"类反馈较 v0.4.0 下降 ≥ 80%；压缩触发时对话不中断、首字延迟可接受；
  2. 归档功能上线 4 周内被知晓率（在聊天更多菜单看到该入口）≥ 50% 助手周活；归档后用户主动查看/编辑记忆的比例形成观测基线；
  3. "全天日程冲突"类打扰反馈归零；定时重叠冲突的二次确认流程零回归；
  4. 聊天中写操作产生的卡片数从"一整串"收敛到"每次操作 1 组受影响对象"；相关负面反馈归零。

### 1.3 非目标（v0.5.0 不做）

- **不做多会话/会话管理**：延续 v0.3.0 起的单会话架构，归档作用于当前唯一会话；不做会话列表、会话命名、会话切换；
- **不做记忆自动提取（除归档外）**：长期记忆只在用户**主动归档**时提取，不在每轮对话后后台静默抓取（成本与隐私可控）；
- **不做记忆编辑/收藏/分享/导出**：记忆支持查看与删除（单条/全部），不支持手工编辑条目内容、不支持导出；
- **不做手动压缩按钮与压缩摘要查看页**：压缩全自动、不可手动触发，摘要不提供独立查看页（仅在聊天历史中有轻量分界标识，见 4.4）；
- **不改变冲突检测的时段语义**：只把全天日程移出冲突判定，定时 × 定时的左闭右开相交、二次确认、循环 90 天扫描规则均不变；
- **不做通知提醒、消息推送**（延续全版本边界）；
- **不做账号体系扩展**：手机号、第三方登录、邮箱换绑、自助找回密码、头像上传仍不做；修改密码能力本身保留（仅删设置页入口）；
- **不做深色模式、字号调节、多语言、PC 端专门适配**；
- **不回溯重写历史消息**：CHAT-01 的卡片收敛只改变新消息的产生规则与渲染折叠规则，不删除、不改写已落库的历史卡片数据。

## 2. 目标用户与使用场景

### 2.1 目标用户

延续 v0.4.0 全体个人用户，本版尤其面向：

- 与助手**连续多轮规划复杂事项**（旅行、周计划、项目排期）的高频用户；
- 希望助手记住自己**长期偏好与固定情况**（作息、称呼、常用清单、长期约束）的用户；
- 日程密集、全天安排（出差/休假/法定假日）与定时日程混用的用户；
- 对界面入口冗余、聊天信息刷屏敏感的体验向用户。

### 2.2 核心使用场景

| 场景 | 描述 |
| --- | --- |
| 长对话不"失忆" | 用户与助手连续讨论 30 轮以上的周末旅行安排，早期定下的出发时间、同行人在第 31 轮仍能被正确引用；用户无感知，界面上仅在历史分界处有一条"更早对话已自动摘要"标识。 |
| 归档开启新话题 | 一个阶段的事情聊完，用户在助手页更多菜单点"归档聊天记录"：系统提炼出"用户习惯早上开站会、周五不安排重会、健身在每周三"等长期记忆，随后当前聊天清空；下次新对话里助手直接按这些已知前提给方案。 |
| 管理记忆 | 用户在系统设置 → 长期记忆页看到全部记忆条目；发现"用户偏好深夜开会"是误读，当场删除该条，之后助手不再据此安排。 |
| 全天日程不再报冲突 | 用户建"周三 全天 出差"，同日已有"09:00 晨会"：保存出差时不再出现冲突提示；在 09:00 晨会之外再建一个"10:00 评审"与 10:30 已有会重叠时，仍照常提示定时冲突。 |
| 入口精简 | 用户打开抽屉：底部只有账号区（进个人信息）与齿轮（进设置），没有退出按钮；想退出时进个人信息页危险区点"退出登录"。个人信息页不再出现"清除聊天记录"；设置页不再出现"修改密码"（改密从个人信息页进入）。 |
| 聊天改日程不刷屏 | 用户日程较多时说"把明天的周会改到下午 4 点"：聊天记录里只出现最终"周会 16:00"一张结果卡，助手为找到周会而查询当天日程的过程不再刷出整屏卡片；用户主动问"我明天有什么安排"时，回答仍正常展示日程列表（条数多时默认折叠）。 |

## 3. 产品整体说明

### 3.1 产品形态（延续）

- 仍为**移动端 Web（H5）**瘦客户端：压缩、记忆提取/注入、冲突判定均在服务端完成，端上仅展示与交互；
- 延续全云端架构：记忆与摘要存云端数据库，端上不缓存；读失败展示错误占位，不展示陈旧数据；
- 延续单会话、DeepSeek 服务端统一代理、Function Calling + SSE 流式、模型可在服务端替换的总体架构。

### 3.2 v0.5.0 变更总览

### 3.4 三种"记忆/清理"机制的关系（关键，避免混淆）

v0.5.0 同时存在三个相近概念，边界如下：

| 机制 | 层级 | 是否删除消息 | 触发方式 | 内容 | 跨会话 |
| --- | --- | --- | --- | --- | --- |
| **上下文自动压缩**（CTX-01） | 会话级短期上下文 | 否（聊天页仍可完整翻看） | 系统自动（超水位） | 旧消息的结构化摘要 + 最近原文窗 | 否 |
| **归档 / 长期记忆**（MEM-01） | 用户级长期记忆 | 是（归档成功后清空当前消息与待确认动作） | 用户主动 | 跨阶段有效的用户事实/偏好，去重合并后持久化 | 是 |
| **清除聊天记录**（既有） | —— | 是 | 用户主动 | 不提取任何内容 | —— |

- 归档与清除**互斥语义**：想"留住点什么再清空"用归档；想"彻底丢弃"用清除；
- 归档（或清除）完成后，该会话的压缩摘要一并失效（消息已清空，无旧内容可概括），下一轮从空对话重建；
- 长期记忆注入与压缩摘要拼接在同一次模型请求中但分区明确：长期记忆描述"用户是谁、有什么长期情况"，压缩摘要描述"本会话早些时候聊了什么"。

## 4. 功能需求一：上下文自动压缩（CTX-01）

### 4.1 触发条件

- 系统在每轮对话组装模型请求时估算上下文体量（系统提示词 + 工具定义 + 长期记忆 + 历史消息 + 本轮用户消息），当估算值达到模型上下文窗口的**安全水位**时，在调用主模型前自动执行一次压缩；
- 安全水位默认 **80%**（服务端可配置，如 `CHAT_COMPACT_THRESHOLD_RATIO=0.8`）；阈值随模型上下文窗口变化，替换模型时只需调配置；
- 压缩采用**水位指针**推进：每次只压缩"上次摘要水位之后、最近原文窗之前"的增量旧消息，同一段历史不重复压缩，避免每轮重复花费 token；
- 压缩在服务端静默完成，用户无任何操作；压缩能力不可关闭、不提供手动入口。

### 4.2 压缩对象与保留窗

| 部分 | 处理 |
| --- | --- |
| 最近 **K 条消息**（默认 K=10，服务端可配置） | **保留原文**参与上下文，保证近期多轮指代（"把它改到下午"）、方案确认链路完整 |
| 更早的消息 | 由一次独立的 LLM 调用压缩为**结构化摘要**，替代原文参与后续上下文 |
| 系统提示词、工具定义、长期记忆（MEM-01） | 永不参与压缩 |

**不得压入摘要、必须留在原文窗的内容（硬边界）**：

1. 最新一条**未确认的方案卡（proposal）**及其所在轮次消息；
2. 任何仍处于待确认状态的危险/批量/冲突确认块（confirm/pending）相关消息；
3. 未决的澄清（clarify）、作用域选择（scope）消息。

即：原文窗的实际起点至少前推到"最近一个未完成交互"之前，宁可少压一段，也不得把等待用户确认的上下文压成摘要。

### 4.3 摘要内容结构

压缩不是流水账，要求产出**结构化、可被后续对话使用**的摘要，固定包含以下分节（无内容的分节省略）：

1. **用户意图与已确定事项**：本轮对话阶段目标、已明确的时间/对象/参数决定；
2. **涉及对象锚点**：对话中操作过的任务、日程的 ID 与标题（沿用现有 buildHistory 的"本轮涉及任务/日程"紧凑锚点策略，摘要中必须保留真实 ID，使"还是那个""把它改了"可解析）；
3. **用户表达的偏好与约束**（仅本会话上下文内的临时偏好，区别于长期记忆）；
4. **未决事项**：聊到但尚未完成、等待后续处理的事。

- 摘要为纯文本分段（供模型读取），单条摘要有 token 上限（默认 ≤ 1000 token，可配置）；
- 多次压缩时，新摘要的输入为"上一份摘要 + 增量旧消息"，产出合并后的新摘要（滚动摘要），避免摘要本身无限增长；
- 压缩只概括对话文本与对象锚点，**不回放历史工具调用与原始工具返回**（与现状 buildHistory 原则一致，防止与云端最新数据状态不一致）。

### 4.4 用户感知与聊天历史

- **聊天页消息记录完整保留、完整可翻**：压缩只改变"发给模型的上下文"，不删除、不折叠、不改写任何已落库消息；
- 在被摘要覆盖的历史段与原文窗分界处，前端显示一条轻量系统分隔文案：**「更早的对话已自动摘要，仍可向上翻看完整记录」**（该标识为渲染层生成，不产生新消息、不需要入库）；
- 压缩触发轮若需等待额外 LLM 调用，SSE 先输出轻量状态提示（如"正在回顾之前的对话…"），避免用户以为卡顿；状态提示为临时流事件，不落入消息历史。

### 4.5 失败与边界

| 情况 | 处理 |
| --- | --- |
| 压缩 LLM 调用失败/超时 | 本轮放弃压缩，按现有"最近消息截断"方式组装上下文正常对话，记录 error 日志与埋点；**不得阻断用户对话、不得报错给用户** |
| 压缩后仍超水位 | 再次扩大压缩范围（进一步缩小保留窗，最小不低于 6 条且满足 4.2 硬边界）；仍超限则按最近窗截断发送，保证请求可发出 |
| 压缩调用进行中用户继续发消息 | 沿用现有单轮串行：压缩完成后再处理下一轮；流式期间发送入口本就受限 |
| 归档/清除会话 | 摘要与水位指针随会话重置（见 3.4） |
| 模型替换导致上下文窗口变化 | 水位比例可配置；窗口变大时下次组装按新窗口重新判定，已存摘要不回滚 |
| 历史消息中的卡片数据已陈旧 | 摘要只记对象 ID 与标题锚点，具体字段沿用现有"卡片渲染时用云端数据刷新"机制，不依赖摘要中的快照值 |

## 5. 功能需求二：归档聊天记录与长期记忆（MEM-01）

### 5.1 归档入口与交互

- 入口：助手页（`/chat`）右上角更多菜单，新增 **「归档聊天记录」**（普通样式，与危险样式的「清除聊天记录」并列）；
- 点击后弹确认层，文案必须同时讲清"得到什么、失去什么"：

  > **归档聊天记录？**
  > 系统会从当前对话中提炼长期记忆并保存，之后与助手的新对话可以使用这些记忆；提炼完成后，当前聊天记录将被清空且不可恢复。任务与日程数据不会被删除。
  > 「归档并清空」 / 「取消」

- 归档过程中（LLM 提取 + 落库 + 清空）展示 loading，更多菜单与发送入口临时禁用，避免并发；
- 成功后：toast「已归档，保存了 N 条长期记忆」，toast 提供「查看」直达长期记忆页；聊天区回到空态引导（与清除后的空态一致），会话标题重置；
- 流式回复进行中禁止归档（入口置灰/提示"助手回复中，请稍候"）。

### 5.2 归档处理流程与失败保护

```
用户确认归档
  → 读取当前会话全部消息（含文本与对象锚点，不含工具原始返回）
  → LLM 提取候选长期记忆（结构化条目，见 5.3）
  → 与该用户已有记忆做去重/合并/更新（语义近似条目合并，不重复保存）
  → 记忆落库成功后，才执行清空：删除消息、删除待确认动作、重置会话标题、
    重置 CTX-01 压缩摘要与水位指针（清空语义复用现有 clear 逻辑）
  → 返回保存条数
```

- **失败保护（硬约束）**：提取失败、去重失败、记忆落库失败任一步发生，**不得清空任何消息**；提示"归档失败，聊天记录未受影响，请稍后重试"；
- 只有"记忆已确认落库"之后才允许执行清空；不允许部分成功（部分记忆保存、消息已删）——落库与清空在服务端按顺序事务性保障；
- 归档时若对话为空或 LLM 未提取到任何值得记忆的内容：不落任何记忆，空对话提示"没有可归档的内容"，非空对话则提示"本次没有提炼到需要长期保留的内容"，并询问是否仍清空（默认按钮"仍然清空"/"取消"），避免用户误以为已保存记忆。

### 5.3 长期记忆的内容边界

**应当提取**（跨会话长期有效的稳定信息）：

| 类别 | 示例 |
| --- | --- |
| 用户情况与称呼 | 昵称/希望被怎么称呼、所在城市、通勤情况 |
| 固定作息与时间偏好 | 习惯早起、午休 12:30、周五不排重会、睡前不安排工作 |
| 常用对象与场景 | 默认清单名称、固定项目名、常用会议名、健身每周三 |
| 明确表达的长期偏好/禁忌 | 安排日程默认提前半小时、不要在周日安排工作、任务默认低优先级 |
| 长期事项背景 | "正在准备 12 月的考试""家里有宠物，出差需要安排"等会持续影响后续安排的事实 |

**不得提取**：

- 一次性日程流水（"明天 10 点开会"）——任务/日程数据本身已在云端，无需记忆；
- 临时上下文（只在本次规划中成立的约束）、情绪性寒暄、与助手能力无关的内容；
- 密码、证件号等敏感凭证类信息（提取提示词明确要求排除，提取结果再经敏感词/模式过滤）；
- 无法确定时效、猜测性的内容（LLM 不得脑补用户没说过的事实）。

每条记忆为一句**自包含陈述**（如"用户每周三 19:00 健身，安排日程时应避开该时段"），附带类别与来源（第几次归档、归档时间）。

**容量控制**：

- 单次归档新增/更新条目数上限默认 **30**（`MEMORY_ARCHIVE_BATCH_LIMIT`）；
- 每用户记忆总条数上限默认 **100**（`MEMORY_MAX_TOTAL`）；达到上限时，新条目与旧条目语义合并；无法合并时淘汰最久未被使用/最旧的条目，淘汰在归档结果中可被用户察觉（记忆页按时间排序，用户可删除不当条目）；
- 注入上下文的记忆总 token 设预算上限（默认 ≤ 800 token），按"近期使用/更新优先"截断，保证记忆不挤占对话窗口。

### 5.4 记忆的使用（注入）

- 每轮模型请求在系统提示词之后以独立分区注入当前有效记忆，分区标题明确（如"以下是用户的长期记忆，仅在与当前任务相关时使用，不得主动向用户背诵记忆条目"）；
- 记忆只影响模型行为，**不作为消息气泡出现在聊天中**，用户不会在对话页看到"记忆：xxx"；
- 记忆删除/全部清空后，下一轮请求即不再注入；正在进行中的 SSE 流不中断、不回溯；
- 提示词约束：模型不得因为记忆存在而跳过必要确认（记忆是弱先验，用户当轮明确表达与记忆冲突时以当轮表达为准，并可在归档时更新记忆）。

### 5.5 长期记忆管理页（/me/memories）

- 入口：①系统设置"对话"分组新增「长期记忆」行（右侧显示条数，如 12 条）；②归档成功 toast 的「查看」；
- 页面结构：
  - 顶部说明：一句话解释记忆来源与用途（"归档聊天记录时自动提炼，用于让助手更了解你的长期情况"）；
  - 记忆列表：每条一行/一卡——记忆内容（陈述句全文）、副信息（类别 + 归档时间）；按归档/更新时间倒序；
  - 单条删除：行尾删除动作（图标按钮或左滑），点击轻确认（"删除这条记忆？删除后助手将不再参考它"）；
  - 底部危险区：**全部删除**（二次确认，红色危险按钮；清空后后续对话零记忆注入）；
  - 空态："还没有长期记忆。在助手页归档一次聊天记录，助手会帮你提炼。"并提供"去助手"跳转；
- 加载失败显示错误占位 + 重试（云端架构，不展示陈旧数据）；删除失败 toast 报错且条目保留；
- 可访问性：删除热区 ≥ 44pt，列表项支持屏幕阅读器朗读内容与删除操作。

### 5.6 数据模型与接口（产品级要求，细节由 SDD 定稿）

- 新增迁移 **010**（纯新增、幂等，沿用 007/008/009 约束）：新建长期记忆表，字段至少包含：所属用户、记忆内容（文本）、类别、来源归档批次/时间、创建时间、更新时间；用户删除即物理删除（或按 SDD 决定的等价可清除方案），注销账号级联删除；
- 压缩摘要的存储（CTX-01）由 SDD 在"会话新增摘要字段/独立摘要表"中定稿，PRD 要求：随会话归属、随清空重置、不外泄接口；
- 新增接口（均为鉴权接口，仅访问本人数据）：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/conversations/:id/archive` | 归档：提取+落库记忆，成功后清空消息；返回提炼条数；处理中/空会话按 5.2 语义返回 |
| GET | `/memories` | 返回记忆列表（内容、类别、归档时间），按时间倒序 |
| DELETE | `/memories/:id` | 删除单条（越权/不存在返回统一 404 语义） |
| POST | `/memories/clear` | 全部删除（危险操作，服务端仅按用户维度删除） |

- 归档接口单独考虑限流与 LLM 成本（如每用户每分钟 ≤ 1 次归档调用）。

### 5.7 隐私与安全

- 记忆属于用户个人数据：仅本人经鉴权后可读写；服务端日志不得记录记忆正文（只记条数/类别/事件）；
- 提取走现有服务端 LLM 统一代理，API Key 不下发端上；
- 敏感信息排除（5.3）+ 提取结果过滤 + 用户可查看/删除，三层控制；
- 注销账号、清除（记忆不受清除影响，仅归档不影响——注意：**"清除聊天记录"不删除已保存的长期记忆**，记忆只能在记忆页删除）。

## 6. 功能需求三：全天日程不进行冲突提醒（EVT-01）

### 6.1 新冲突语义（取代 v0.4.0 的 all_day 弱化提示）

| 组合 | v0.4.0 行为 | v0.5.0 行为 |
| --- | --- | --- |
| 全天 × 全天（同日/跨日相交） | 弱化提示（all_day 级冲突） | **不提示冲突** |
| 全天 × 定时（同日时段相交） | 弱化提示（all_day 级冲突） | **不提示冲突** |
| 定时 × 定时（时段重叠） | 冲突提示 + 二次确认（overlap） | **不变** |

- 判定原则一句话：**只要参与比较的任一方是全天日程，就不产生时间冲突提醒**；冲突检测只服务于"具体时段被占用"的场景；
- 全天标识仍以 `all_day=true` 为准（全天事件时间为当日 00:00–次日 00:00 的既有存储不变，数据零迁移）。

### 6.2 生效面（双入口 + 全链路一致）

| 链路 | 变更 |
| --- | --- |
| 手动新建/编辑日程 | 全天日程保存不再返回冲突；定时日程的冲突列表中不再包含全天日程 |
| 循环系列创建/补挂规则的 90 天扫描 | 扫描展开时，全天实例/与全天单日相交不再计入冲突日期分组；定时 × 定时重叠照常分组提示 |
| 单次改期（仅本次/本次及以后） | 同上，全天相关不阻断、不提示 |
| LLM 对话（create_event/update_event/batch_update_events） | 工具层不再因全天相交返回 need_conflict_confirmation；助手不再就全天安排发冲突陈述；定时重叠的确认链路不变 |
| 日程详情"时间重叠"角标/文案 | 与全天事件的重叠不再展示 |

### 6.3 边界

- 本变更只影响"提醒/阻断"，不影响全天日程的任何展示（月历、当日列表全天分组、详情、卡片照常）；
- 不影响冲突之外的校验（时间先后、结束条件、4011 参数类错误等）；
- 定时 × 定时冲突的 4009、`confirm_conflict` 重提、循环冲突按日期分组、用户坚持后放行等机制全部保留；
- 任务日程禁循环（4016）等既有门控与本项无关，保持不变。

## 8. 功能需求五：聊天日程卡片收敛（CHAT-01）

### 8.1 问题根因

助手在对话中执行写操作前，通常先调用只读工具（`list_events`/`search_events`/`get_event` 等）定位对象；现有编排把**任何**携带日程/任务数据的工具结果都渲染成 `cards` 卡片块并落入聊天记录。于是"改一个日程"常常伴随"当天全部日程"的卡片串；写操作完成后模型还可能再查一次当日安排"汇报结果"，二次刷屏。

### 8.2 新规则：区分过程数据与结果展示

以"一条用户消息 → 助手回复结束"为一个处理轮次：

| 轮次类型 | 只读工具结果（list/search/get） | 写工具结果（create/update/delete/complete 等） |
| --- | --- | --- |
| **本轮发生了写操作** | **不产生卡片**（数据照常供模型使用，用户不可见） | 产生结果卡片，**仅含本次实际受影响的对象**（单个/本批），不附带同范围其他对象 |
| **本轮纯查询**（"我明天有什么安排"） | 正常产生查询结果卡片 | —— |

- 多候选澄清（clarify 候选卡片）、危险/批量影响范围确认（confirm 卡片）是**交互必需**，不属于"过程数据"，照常展示，规则不变；
- 写操作结果卡只含受影响对象的要求**主要通过提示词约束 + 工具返回裁剪实现**：现有写工具本身已只返回被改动对象，需在系统提示词中新增明确约束——"写操作完成后不得再调用 list_events 等查询工具向用户铺陈全天/多日安排，结果只用一句话 + 受影响对象卡片回应"；
- 被隐藏的过程查询结果仍按现有方式供模型使用（含 ID 锚点），模型理解能力不受影响；这些过程数据也不进入 CTX-01 的摘要素材以外的任何持久展示（摘要按 4.3 只记锚点）。

### 8.3 大结果折叠（纯查询轮）

- 纯查询轮的结果卡片数量超过 **10 项**时，卡片组默认折叠：显示"共 N 项安排 · 点击展开"，展开后完整浏览；折叠态不影响模型拿到完整数据；
- 阈值 10 为默认值（UXUI 可在 8~15 间定稿），同一轮多个结果组合并计数；
- **历史已落库的大卡片**：新版渲染层同样按 10 项阈值默认折叠（仅展示层折叠，不改写历史数据、不新增请求），保证升级后翻看旧聊天也不再被长卡片刷屏。

### 8.4 边界

| 情况 | 处理 |
| --- | --- |
| 一轮内先查后改（最典型） | 查询卡隐藏，仅最终改动卡可见 |
| 一轮内先查后改，且写操作返回需要冲突/危险确认 | 过程查询隐藏；确认卡正常展示；确认通过后结果卡只含受影响对象 |
| 一轮内查了但最终没改成（用户取消/确认拒绝） | 该轮无写成功结果，过程查询仍不展示；助手文本说明结果即可 |
| 纯查询 + 顺带一句修改 | 以本轮实际成功的写操作为准：写成功则只展示改动卡，查询清单不铺展（模型可在文本中口头回答查询结论） |
| 用户连续纯查询 | 每轮各自独立，均正常展示结果卡（各自按阈值折叠） |
| 任务类过程查询（list_tasks 等） | 同等规则：写操作轮中的任务过程查询不落地为卡片 |

## 9. 非功能性需求

### 9.1 性能

- 压缩触发轮：压缩 LLM 调用 P95 ≤ 3s（DeepSeek flash 档），期间以 SSE 状态提示占位；压缩只在超水位时发生，常规轮次零额外调用、零额外延迟；
- 归档：提取调用 P95 ≤ 8s（全量对话），端上 loading 可接受；归档后清空与现有 clear 同量级；
- 长期记忆注入为小表按用户读取（单用户 ≤ 100 条），要求服务端进程内短期缓存，注入组装额外耗时 P95 ≤ 20ms；
- 记忆列表页首屏 P95 ≤ 300ms；单条删除 P95 ≤ 200ms；
- 移除全天冲突判定后，冲突查询路径不得劣化（查询条件收窄，预期持平或更优）；
- 卡片收敛不新增任何接口请求，过程数据隐藏在服务端编排层完成。

### 9.2 兼容性与数据

- 迁移 010 为纯新增（新表），幂等可重复执行；存量会话、消息、事件、任务数据零回填、零语义漂移；
- CTX-01 首次上线后，老会话在下一次超水位时正常压缩即可，不需要预压缩；现有 `CHAT_HISTORY_LIMIT=20` 配置保留，语义过渡为"最近原文窗条数 K"的缺省来源之一（具体配置方案由 SDD 定稿，保证不配置也能运行）；
- EVT-01 为判定逻辑变更，不涉及历史数据；升级后曾因全天被弱化提示过的场景不再提示，不需要数据修复；
- UI-01/02/03 仅删除端上入口，对应能力（clear/change-password/logout）与接口全部保留；
- 旧客户端与新服务端兼容期内：新增字段/接口为增量，不破坏旧版聊天与登录。

### 9.3 隐私与安全

- 压缩摘要与长期记忆均为用户个人数据：归属校验、日志不记正文（摘要可记长度与触发事件）、注销级联删除；
- 记忆提取结果须经敏感信息过滤（5.3）；归档与记忆接口纳入现有鉴权与限流体系；
- 长期记忆注入构成新的提示词注入面：记忆内容为"数据"而非"指令"，系统提示词需明确隔离（记忆中的命令式文本不得被当作指令执行，如记忆里出现"忽略之前的规则"应被忽略），安全评审覆盖该用例；
- 记忆删除必须在下一轮上下文物理失效，不允许缓存继续注入已删条目。

### 9.4 可观测性（新增埋点/日志）

- `chat_compaction_triggered / success / fail`（含压缩消息条数、摘要 token、耗时、失败原因）；
- `chat_archive_click / success / fail / empty`（归档发起、成功、失败、无记忆内容）、`memory_saved_count`（每次归档新增/合并/淘汰条数分布）；
- `memory_page_view`、`memory_delete_one`、`memory_delete_all`、`memory_injected_tokens`（注入预算命中截断的比例）；
- `conflict_allday_suppressed`（全天冲突被抑制次数，抽样观测，用于确认语义变更覆盖面）；
- `chat_tool_cards_hidden`（写操作轮被隐藏的过程查询卡次数/数据条数）、`chat_cards_collapsed`（折叠卡展开率）；
- 错误日志：压缩失败、归档"未清空保护"触发、记忆敏感过滤命中、已删记忆仍被注入（异常）。

## 10. 关键业务流程与验收标准

### 10.1 关键业务流程

**流程一：长对话自动压缩**

```
第 1~12 轮正常对话
第 13 轮组装上下文 → 估算超 80% 水位
  → SSE 临时状态"正在回顾之前的对话…"
  → 取第 1..3 条旧消息 → LLM 滚动压缩为结构化摘要（含任务/日程 ID 锚点）
  → 摘要 + 第 4~12 条原文 + 长期记忆 + 本轮消息 → 主模型正常回复
  → 聊天页历史无任何删除，分界处显示"更早的对话已自动摘要"
若压缩服务失败 → 静默按最近消息截断发送，用户无感知，日志记录
```

**流程二：归档沉淀长期记忆**

```
/chat 更多 → 归档聊天记录 → 二次确认（说明提炼记忆+清空记录）
  → 读取全量消息 → LLM 提取候选记忆（排除日程流水/敏感信息）
  → 与已有记忆语义去重合并（≤30 条/次，总量 ≤100）
    ├─ 提取/落库失败 → 消息一条不删，提示稍后重试
    └─ 落库成功 → 清空消息与待确认动作、重置标题与压缩摘要
        → toast"已归档，保存了 N 条长期记忆"（可点查看 → /me/memories）
新会话："帮我安排周三晚上的事" → 模型读到记忆"周三 19:00 健身" → 主动避开该时段
```

**流程三：记忆删除即时生效**

```
/settings → 长期记忆 → 删除"偏好深夜开会"
  → DELETE /memories/:id → 列表移除 → 下一轮模型请求不再注入该条
全部删除 → 危险二次确认 → 后续对话零记忆（已保存的日程/任务数据不受影响）
```

**流程四：全天日程无冲突**

```
建"周三 全天 出差"（同日已有 09:00 晨会）→ 直接保存成功，无冲突提示
同日再建"10:00 评审"（与 10:00 已有会重叠）→ overlap 冲突提示 → 坚持后 confirm 保存
循环"每个工作日 09:00 站会"90 天扫描命中的全天安排不计入冲突日期分组
```

**流程五：聊天改日程卡片收敛**

```
日程较多的一天，用户："把明天的周会改到下午 4 点"
  → 助手过程调用 list_events 定位（结果不产生卡片）
  → update_event 成功 → 聊天记录仅出现 1 张"周会 16:00"结果卡 + 一句话回应
用户："我明天有什么安排"（纯查询，12 项）
  → 结果卡组默认折叠"共 12 项安排 · 点击展开"
```

**流程六：入口收敛**

```
抽屉：无退出按钮；账号区 → /me，齿轮 → /settings
/me：无"清除聊天记录"；有"修改密码/退出登录/注销账号"
/settings：无"账号安全"分组；"对话"分组含"长期记忆（N 条）/清除聊天记录"
```

### 10.2 验收标准

**CTX-01 上下文自动压缩**

1. 构造超过水位的长对话：第 N 轮自动触发压缩，对话正常完成且早期决定（含任务/日程 ID 指代）可被正确引用；常规短对话不触发、零额外延迟；
2. 压缩只改模型上下文：聊天页全部历史消息仍可完整翻看，分界文案出现一次；系统提示词/工具定义/长期记忆不被压缩；
3. 未确认方案卡、待确认危险/冲突块、未决澄清始终保留在原文窗，不被压入摘要；压缩后确认链路可正常完成；
4. 压缩服务失败/超时时对话不中断、无用户可见报错，回退最近消息截断，日志与埋点完整；
5. 滚动压缩不重复概括同一段历史；归档/清除后摘要与水位重置，空对话正常开始。

**MEM-01 归档与长期记忆**

6. 助手更多菜单存在"归档聊天记录"，确认文案同时说明"提炼记忆"与"清空记录"；回复中入口禁用；
7. 归档成功：记忆落库（提取类别符合 5.3 白名单、无日程流水/无敏感凭证/无脑补）、与旧记忆去重合并、消息与待确认动作清空、标题与压缩摘要重置、toast 显示条数并可跳转记忆页；
8. 提取或落库失败时消息零清空并提示重试；空会话/无记忆内容按 5.2 分支处理，不产生"假成功"；
9. 容量规则生效：单次 ≤30 条、总量 ≤100 条，超限时合并/淘汰行为正确；
10. 记忆页可查看（内容/类别/时间/倒序/条数入口）、单条删除（轻确认）、全部删除（危险二次确认）；空态、错误占位、删除失败保留均正确；
11. 记忆在下一轮按分区注入且不渲染为消息；删除/清空后下一轮立即不注入，进行中的 SSE 不受影响；注入超预算时按优先级截断；
12. "清除聊天记录"不删除长期记忆；注销账号级联删除记忆；归档接口鉴权、归属校验、限流有效；提示词注入类记忆（"忽略规则"等）不被执行。

**EVT-01 全天冲突**

13. 全天 × 全天、全天 × 定时在手动创建、编辑、单次改期、循环 90 天扫描、LLM 工具全链路均无冲突提示与阻断；
14. 定时 × 定时重叠的 4009/二次确认/`confirm_conflict`/循环按日期分组行为与 v0.4.0 完全一致，零回归；
15. 全天日程展示（月历/列表分组/详情/卡片）不受影响；全天相关计数埋点可查。

**UI-01/02/03 入口收敛**

16. `/me` 无"清除聊天记录"行与弹层，其余行（昵称/邮箱/注册时间/修改密码/退出/注销）功能正常；
17. `/settings` 无"账号安全"分组与"修改密码"行；`/me/password` 改密全流程（含吊销其他凭证）正常；
18. 抽屉无"退出"按钮，账号区与齿轮功能正常，焦点陷阱/ARIA 回归通过；`/me`、`/settings` 两处退出登录正常；
19. 清除记录仍可从助手菜单与设置页正常完成；能力与接口无下线。

**CHAT-01 卡片收敛**

20. 写操作轮中的只读查询（日程/任务）不产生聊天卡片；结果卡仅含实际受影响对象；提示词约束下写后不再主动铺陈全天日程；
21. clarify 候选卡、confirm 影响范围卡在任何轮次照常展示并可交互；
22. 纯查询轮结果卡正常展示，>10 项默认折叠可展开；历史旧消息中的大卡片在新版同样折叠且不触发额外请求、不改写数据；
23. "先查后改但未改成""查询+顺带修改"等边界轮次按 8.4 呈现；模型定位对象的准确率不因隐藏过程数据而下降（专项回归）。

**非功能**

24. 迁移 010 幂等、可重复执行，类生产数据演练通过；存量数据零回填；性能指标（9.1）达标；
25. 隐私安全评审通过：记忆/摘要归属与日志规范、敏感过滤、提示词注入隔离、已删记忆零注入；9.4 埋点全部可查。
