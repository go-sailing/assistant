## 1. 设计概述

### 1.1 系统边界（增量）

v0.7.0 在既有"App ↔ 服务端 REST + 服务端统一 LLM"边界之外，**新增一条对外集成面**：

```
                       ┌────────────────────────────────────────────┐
   移动端 H5（App） ──REST/SSE──▶│  个人助手服务端（Node/Express 单体）        │
                       │                                            │
                       │  ┌──────────────┐   ┌──────────────────┐  │
                       │  │ Task/Event/  │   │ AgentService     │  │
                       │  │ Chat/Memory… │◀──│ （代理域唯一入口）│  │
                       │  └──────┬───────┘   └────────┬─────────┘  │
                       │         │  领域唯一入口原则    │            │
                       │  ┌──────┴────────────────────┴─────────┐  │
                       │  │  REST 路由（/api/v1）│ MCP 接入层（/mcp）│  │
                       │  └─────────────────────────┬───────────┘  │
                       └────────────────────────────┼──────────────┘
                                                    │ JSON-RPC 2.0 over HTTP
                                    外部智能工具（Claude Code / opencode / pi agent…）
                                            作为 MCP 客户端，持代理凭据接入
```

- **新增对外协议**：`POST /mcp`（MCP 服务端，JSON-RPC 2.0 over HTTP，无状态）；
- **新增鉴权通道**：代理凭据（`Authorization: Bearer <agent_token>`），与用户 JWT/refresh **完全并列、互不通用**；代理凭据只能落在 `/mcp` 端点；
- **不做**（见 PRD 1.3）：服务端主动推送、stdio 托管、代理写任务/日程/项目、执行产物传输、实时日志流、自动重试策略。

### 1.2 设计目标与手段

| 目标 | 手段 |
| --- | --- |
| 指派即自动执行（无二次触发） | 指派在**同一事务**内完成"写指派关系 + 入队 + 写记录"；提交后同进程唤醒等待者（waiter），代理侧长轮询即刻返回；端上不再出现任何"通知"接口与按钮 |
| 代理接入通用（多工具） | 服务端实现 MCP 标准的 tools 子集（`initialize` / `tools/list` / `tools/call` / `ping`），代理工具零改造接入；协议层错误与业务错误分离（JSON-RPC error vs `isError`） |
| 领取不重不漏 | 领取为条件 `UPDATE ... WHERE agent_state='pending' AND agent_id=$x` 的**原子操作**，以 `rowCount` 判定冲突；队列不产生重复项 |
| 同清单约束随清单一起消失 | 任务读路径去掉 `task_lists` JOIN；创建任务落"用户默认清单"（隐式兜底），清单对外能力整体下线，4014 编号保留无触发面 |
| 页面分离不动服务端语义 | 项目/任务查询复用既有 `task_type` + `root_only` 过滤；前端以路由与页面拆分实现分离，服务端仅做"清单参数下线"的收窄 |
| 手势缺陷只改判定 | CAL-03 以"起手快照"替代"实时 scrollTop"判定，逐行最小改动，手势参数与视觉零变化 |

### 1.3 核心概念与领域不变量

**概念**

| 概念 | 定义 |
| --- | --- |
| 智能体代理（agent） | `agents` 表一行：代表一个外部智能工具实例的接入身份，归属某个 user |
| 代理凭据（agent token） | 与代理 1:1 的密钥；库中只存 `sha256` 摘要（`token_hash`）与前缀（`token_prefix`）；明文仅创建/重置响应返回一次 |
| 指派（assign） | 建立 `tasks.agent_id` 关系，任务 `agent_state: none → pending`（**同事务**），并写 `agent_task_logs(assigned)` |
| 领取（claim） | 代理把 `pending → running` 的原子操作（同事务写 `claimed` 日志） |
| 回报（report） | 代理写 `progress` 日志、或把 `running → succeeded`（任务同时 `completed`）/ `running → failed` |
| 重新执行（retry） | 用户把 `failed → pending`（服务端侧），并写 `retried` 日志 |
| 代理已删除（running without agent） | `agent_state='running' AND agent_id IS NULL`：代理被删除后保留的执行中任务，回报必然被拒（4019），等待用户取消指派或重新指派 |

**领域不变量（必须在 AgentService 单点保证）**

| # | 不变量 |
| --- | --- |
| I1 | `agent_state='none'` ⟺ `agent_id IS NULL` 且 `agent_queued_at/agent_claimed_at/agent_finished_at/agent_result` 全为 NULL |
| I2 | `agent_state IN ('pending','running')` → `agent_finished_at IS NULL`；`agent_state IN ('succeeded','failed')` → `agent_finished_at IS NOT NULL` |
| I3 | `agent_state='pending'` → `agent_claimed_at IS NULL`（队列项未被领取） |
| I4 | 一个任务同一时刻至多一个 `agent_id`；`agent_state='pending'` 时该任务在代理队列中恰好出现一次（不重复入队） |
| I5 | 代理可以读取/回报的任务集合 = `{ tasks | user_id = agent.user_id AND agent_id = agent.id }`（最小权限，集合外一律"不存在"） |
| I6 | 代理侧**只能**改 `agent_*` 与（回报完成时的）`status/completed_at`；不得改标题/备注/归属/项目/日程 |
| I7 | 项目任务（`task_type='project'`）不参与指派（4021） |
| I8 | 已完成任务（`status='completed'`）不参与指派与重新执行（4021） |
| I9 | 清单（task_lists）在 v0.7.0 后不再参与任何用户可见语义；任务 `list_id` 恒为用户默认清单 |

## 2. 总体架构（增量）

### 2.1 架构变化

1. **新增 MCP 接入层**（`src/server/src/mcp/`）：Express 路由 + JSON-RPC 处理 + 工具注册表 + 长轮询等待器，**不引入任何新依赖**（协议为纯 JSON-RPC 2.0；工具入参校验复用 `zod`）；
2. **新增 AgentService**（`src/server/src/modules/agent/`）：代理 CRUD、凭据、状态机、队列、日志，作为**代理域唯一入口**（REST 路由、MCP 工具、LLM 工具三条入口共用）；
3. **清单能力下线**：`list.routes.ts` 摘除挂载；`list.service.ts` 收敛为内部兜底（`getDefault` / `createDefaultList`）；`app.ts` 删除 `/api/v1/lists` 鉴权挂载；
4. **任务读路径瘦身**：`TASK_SELECT` 去掉 `JOIN task_lists`；`buildConditions` 去掉 `list_id`；`resolveListId` 替换为 `getDefaultListId`；
5. **前端页面重组**：新增 `/projects*`、`/agents*` 两组路由；`/tasks*` 纯化；`/lists` 重定向；CAL-03 手势判定修复。

### 2.4 关键技术决策（本版需要评审确认的技术项）

| # | 决策点 | 结论 | 理由 |
| --- | --- | --- | --- |
| T1 | MCP 实现方式 | **自实现最小 MCP 子集**（JSON-RPC 2.0 over HTTP，零新增依赖），不引入 `@modelcontextprotocol/sdk` | 本版只需要 tools 能力；协议为纯 JSON；官方 SDK 会引入依赖树与 ESM/构建复杂度，与项目"零新增依赖"基线冲突 |
| T2 | MCP 传输形态 | **无状态**：单次 `POST /mcp` 请求-响应（`application/json`）；不返回 `Mcp-Session-Id`；`GET /mcp` 与 `DELETE /mcp` 返回 405 | 本版无服务端主动推送需求，长轮询在单次请求内完成；无状态免去会话表与粘性路由 |
| T3 | 协议版本 | 支持 `2025-06-18` 与 `2025-03-26`；客户端请求不在此列时按规范返回服务端支持的最新版本 | 覆盖主流客户端；不支持的版本由客户端自行决定是否继续 |
| T4 | "自动下发"的实时机制 | **长轮询**（`wait_agent_task`，服务端上限 25s）+ 同进程事件唤醒 + 2s 兜底轮询 | 指派后 ≤10s 可达（实际毫秒级）；避免引入 WebSocket/SSE 与推送基础设施 |
| T5 | 领取幂等与冲突 | 条件 `UPDATE ... WHERE agent_state='pending' AND agent_id=$x RETURNING id`，`rowCount=0` 即冲突 → 4020 | 单条 SQL 原子，无需显式锁；防重复领取与并发抢单 |
| T6 | 代理凭据存储 | `sha256` 摘要 + 前缀；明文仅创建/重置响应返回一次 | 沿用 refresh token 的摘要做法；库泄露不可逆推 |
| T7 | 清单数据处置 | **不删表不删列**；迁移 013 把任务归位到各用户默认清单并删除自定义清单行 | 回滚成本低、外键不破；PRD 决议 #15 |
| T8 | 4014 处置 | 保留编号与工厂，删除所有触发点 | 与 v0.6.0 对 4013/4015 的处理一致 |
| T9 | 端上埋点落地 | 后端事件用既有 `logger.info('<event>')`；**端上事件不新增上报通道**，由"服务端等效事件 + 测试期断言"承接（见 14.2 口径说明） | 项目无分析 SDK；不为此新增依赖与服务端上报接口 |
| T10 | 执行记录保留 | 每任务写后裁剪至最近 50 条（`AGENT_LOG_KEEP`） | 防止长跑任务日志无限增长 |

## 3. 数据模型与迁移（012 / 013）

### 3.1 agents 表

| 列 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | SERIAL | PK | |
| user_id | INTEGER | NOT NULL REFERENCES users(id) ON DELETE CASCADE | 归属用户 |
| name | VARCHAR(50) | NOT NULL | 代理名称，用户内唯一（大小写不敏感，见索引） |
| kind | VARCHAR(24) | NOT NULL | 受控枚举：`claude_code` / `opencode` / `pi_agent` / `custom` |
| kind_label | VARCHAR(30) | NOT NULL | 展示名：预设写 'Claude Code' / 'opencode' / 'pi agent'；custom 写用户输入 |
| description | VARCHAR(200) | NULL | 描述/用途 |
| status | VARCHAR(16) | NOT NULL DEFAULT 'enabled' | `enabled` / `disabled` |
| token_hash | CHAR(64) | NOT NULL, UNIQUE | 凭据 sha256（hex） |
| token_prefix | VARCHAR(16) | NOT NULL | 明文前缀，用于端上展示（如 `ak_live_7f3c`） |
| last_seen_at | TIMESTAMPTZ | NULL | 最近一次成功 MCP 调用（节流写入，见 5.3） |
| created_at / updated_at | TIMESTAMPTZ | NOT NULL DEFAULT now() | |

索引与约束：

```sql
CREATE UNIQUE INDEX uniq_agents_user_name ON agents (user_id, lower(btrim(name)));
CREATE INDEX idx_agents_user ON agents (user_id, status, last_seen_at DESC);
```

### 3.2 tasks 代理维度列

| 列 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| agent_id | INTEGER | REFERENCES agents(id) **ON DELETE SET NULL** | 当前指派代理；NULL 表示未指派或"代理已删除" |
| agent_state | VARCHAR(16) | NOT NULL DEFAULT 'none' | `none` / `pending` / `running` / `succeeded` / `failed` |
| agent_queued_at | TIMESTAMPTZ | NULL | 指派即入队时间 |
| agent_claimed_at | TIMESTAMPTZ | NULL | 领取时间 |
| agent_finished_at | TIMESTAMPTZ | NULL | 终态时间（succeeded/failed） |
| agent_result | VARCHAR(2000) | NULL | 结果摘要（成功）或失败原因 |

> `ON DELETE SET NULL` 仅作**兜底**：正常删除代理走 AgentService 的显式状态迁移（3.3 / 4.4），保证 `I1/I2` 仍成立；直接删行（如运维误操作）会导致 `state='running' AND agent_id IS NULL`，语义等同"代理已删除"，不会产生脏读。

索引：

```sql
-- 队列：按代理找待领取（部分索引，最热）
CREATE INDEX idx_tasks_agent_queue ON tasks (agent_id, agent_queued_at)
  WHERE agent_state = 'pending';
-- 代理绑定任务列表（按状态筛选）
CREATE INDEX idx_tasks_user_agent ON tasks (user_id, agent_id, agent_state);
-- 端上任务列表按执行状态展示
CREATE INDEX idx_tasks_user_agent_state ON tasks (user_id, agent_state);
```

```sql
-- ============================================================
-- 012_agent_proxy.sql
-- v0.7.0 智能体代理：agents 表 + tasks 代理执行维度 + 执行日志表。
-- 幂等可重复执行：IF NOT EXISTS + pg_constraint 系统目录判定。
-- 执行顺序：① agents → ② tasks 加列 → ③ 约束 → ④ 日志表 → ⑤ 索引。
-- ============================================================

-- ① 代理表
CREATE TABLE IF NOT EXISTS agents (
  id            SERIAL PRIMARY KEY,
  user_id       INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  name          VARCHAR(50) NOT NULL,
  kind          VARCHAR(24) NOT NULL,
  kind_label    VARCHAR(30) NOT NULL,
  description   VARCHAR(200),
  status        VARCHAR(16) NOT NULL DEFAULT 'enabled',
  token_hash    CHAR(64) NOT NULL,
  token_prefix  VARCHAR(16) NOT NULL,
  last_seen_at  TIMESTAMPTZ,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

COMMENT ON TABLE agents IS 'v0.7.0 智能体代理：外部 MCP 工具的接入身份；token 只存 sha256 摘要';

DO $$
BEGIN
  IF NOT EXISTS (
    SELECT 1 FROM pg_constraint
    WHERE conname = 'ck_agents_kind' AND conrelid = 'agents'::regclass
  ) THEN
    ALTER TABLE agents ADD CONSTRAINT ck_agents_kind
      CHECK (kind IN ('claude_code', 'opencode', 'pi_agent', 'custom'));
  END IF;
  IF NOT EXISTS (
    SELECT 1 FROM pg_constraint
    WHERE conname = 'ck_agents_status' AND conrelid = 'agents'::regclass
  ) THEN
    ALTER TABLE agents ADD CONSTRAINT ck_agents_status
      CHECK (status IN ('enabled', 'disabled'));
  END IF;
END $$;

CREATE UNIQUE INDEX IF NOT EXISTS uniq_agents_user_name
  ON agents (user_id, lower(btrim(name)));
CREATE UNIQUE INDEX IF NOT EXISTS uniq_agents_token_hash
  ON agents (token_hash);
CREATE INDEX IF NOT EXISTS idx_agents_user
  ON agents (user_id, status, last_seen_at DESC);

-- ② tasks 代理执行维度（存量零回填：agent_state 默认 none）
ALTER TABLE tasks
  ADD COLUMN IF NOT EXISTS agent_id INTEGER REFERENCES agents(id) ON DELETE SET NULL,
  ADD COLUMN IF NOT EXISTS agent_state VARCHAR(16) NOT NULL DEFAULT 'none',
  ADD COLUMN IF NOT EXISTS agent_queued_at TIMESTAMPTZ,
  ADD COLUMN IF NOT EXISTS agent_claimed_at TIMESTAMPTZ,
  ADD COLUMN IF NOT EXISTS agent_finished_at TIMESTAMPTZ,
  ADD COLUMN IF NOT EXISTS agent_result VARCHAR(2000);

COMMENT ON COLUMN tasks.agent_state IS
  '代理执行状态：none=未指派，pending=已指派并自动入队待领取，running=执行中（agent_id 为空表示代理已删除），succeeded=代理回报完成，failed=代理回报失败';

-- ③ 一致性约束（系统目录判定，幂等）
DO $$
BEGIN
  IF NOT EXISTS (
    SELECT 1 FROM pg_constraint
    WHERE conname = 'ck_tasks_agent_state' AND conrelid = 'tasks'::regclass
  ) THEN
    ALTER TABLE tasks ADD CONSTRAINT ck_tasks_agent_state
      CHECK (agent_state IN ('none', 'pending', 'running', 'succeeded', 'failed'));
  END IF;
  IF NOT EXISTS (
    SELECT 1 FROM pg_constraint
    WHERE conname = 'ck_tasks_agent_queued' AND conrelid = 'tasks'::regclass
  ) THEN
    -- 非未指派态必须已入队（I1 的弱化形式；其余由 AgentService 单点保证）
    ALTER TABLE tasks ADD CONSTRAINT ck_tasks_agent_queued
      CHECK (agent_state = 'none' OR agent_queued_at IS NOT NULL);
  END IF;
  IF NOT EXISTS (
    SELECT 1 FROM pg_constraint
    WHERE conname = 'ck_tasks_agent_finished' AND conrelid = 'tasks'::regclass
  ) THEN
    -- 终态必须有结束时间；进行中必须没有（I2）
    ALTER TABLE tasks ADD CONSTRAINT ck_tasks_agent_finished
      CHECK ((agent_state IN ('succeeded', 'failed')) = (agent_finished_at IS NOT NULL));
  END IF;
END $$;

-- ④ 执行日志（时间线）
CREATE TABLE IF NOT EXISTS agent_task_logs (
  id          BIGSERIAL PRIMARY KEY,
  user_id     INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  task_id     INTEGER NOT NULL REFERENCES tasks(id) ON DELETE CASCADE,
  agent_id    INTEGER REFERENCES agents(id) ON DELETE SET NULL,
  agent_name  VARCHAR(50),
  action      VARCHAR(24) NOT NULL,
  content     TEXT,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

DO $$
BEGIN
  IF NOT EXISTS (
    SELECT 1 FROM pg_constraint
    WHERE conname = 'ck_agent_logs_action' AND conrelid = 'agent_task_logs'::regclass
  ) THEN
    ALTER TABLE agent_task_logs ADD CONSTRAINT ck_agent_logs_action
      CHECK (action IN ('assigned','unassigned','claimed','progress','succeeded','failed','retried'));
  END IF;
END $$;

CREATE INDEX IF NOT EXISTS idx_agent_logs_task ON agent_task_logs (task_id, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_agent_logs_user ON agent_task_logs (user_id, created_at DESC);

-- ⑤ 代理任务索引
CREATE INDEX IF NOT EXISTS idx_tasks_agent_queue
  ON tasks (agent_id, agent_queued_at) WHERE agent_state = 'pending';
CREATE INDEX IF NOT EXISTS idx_tasks_user_agent
  ON tasks (user_id, agent_id, agent_state);
CREATE INDEX IF NOT EXISTS idx_tasks_user_agent_state
  ON tasks (user_id, agent_state);
```

**迁移 012 的正确性要点**

| 关注点 | 结论 |
| --- | --- |
| 存量数据 | `agent_state` DEFAULT `'none'`，`ADD COLUMN` 不重写表；存量任务无 `agent_*` 关联，`ck_tasks_agent_queued` / `ck_tasks_agent_finished` 天然满足 |
| 约束顺序 | 先加列（含默认值）再校验；三条 CHECK 在加列后校验存量行（全部 `none` + 全 NULL → 通过） |
| 可重跑 | 表/索引/列均 `IF NOT EXISTS`；约束以 `pg_constraint` 判定；重跑为 no-op |
| 外键删除语义 | `tasks.agent_id` 为 SET NULL（兜底），`agent_task_logs.agent_id` 为 SET NULL 且冗余 `agent_name` 快照，保证日志可读 |
| 回滚 | 新增表/列/索引对 v0.6.0 代码不可见（旧代码不读不写），可直接回滚 |

```sql
-- ============================================================
-- 013_task_list_retire.sql
-- v0.7.0 清单功能下线：任务归属一次性归位到各用户默认清单，
-- 并清理自定义清单行。保留 task_lists 表与 tasks.list_id 列。
-- 幂等：三步均为条件写，重跑为 no-op。
-- ============================================================

-- ① 兜底：保证每个用户都存在一条默认清单（异常数据修复）
INSERT INTO task_lists (user_id, name, is_default)
SELECT u.id, '默认清单', TRUE
FROM users u
WHERE NOT EXISTS (
  SELECT 1 FROM task_lists l WHERE l.user_id = u.id AND l.is_default = TRUE
);

-- ② 任务归位：全部任务（含项目与项目成员）list_id → 该用户默认清单
UPDATE tasks AS t
SET list_id = d.id
FROM task_lists AS d
WHERE d.user_id = t.user_id
  AND d.is_default = TRUE
  AND t.list_id <> d.id;

-- ③ 清理自定义清单：仅删除已无任务引用的非默认清单（保留守卫，绝不误删）
DELETE FROM task_lists AS l
WHERE l.is_default = FALSE
  AND NOT EXISTS (SELECT 1 FROM tasks AS t WHERE t.list_id = l.id);
```

**幂等与安全论证**

| 关注点 | 结论 |
| --- | --- |
| ① 幂等 | 已存在默认清单的用户不满足 `NOT EXISTS`，不插入；`uniq_lists_default` 部分唯一索引保证不会为同一用户插入第二条默认清单 |
| ② 幂等 | 归位后 `t.list_id = d.id`，条件 `t.list_id <> d.id` 不再成立，重跑零更新；`UPDATE ... FROM` 借助 `idx_lists_user` 与 `uniq_lists_default` 定位默认清单 |
| ③ 安全 | `DELETE` 带 `NOT EXISTS` 子查询守卫：任何仍被任务引用的清单都不会被删，即使有并发写入也安全；删除顺序在归位之后，故正常情况下自定义清单的引用已被清空 |
| 数据零丢失 | 仅改 `tasks.list_id` 与删除"空的自定义清单行"；任务、项目、成员关系、完成状态、`events.task_id` 关联全部不变 |
| 外键 | `tasks.list_id` 为 NOT NULL + RESTRICT，归位先于删除，顺序不可颠倒（已在脚本注释中固定执行顺序） |
| 不可逆点 | 自定义清单的名称信息随之删除，回滚 v0.6.0 后无法恢复原归属（PRD 6.4 已接受该代价） |
| 大库耗时 | 单条 `UPDATE` 按任务数线性；演练需在 v0.6.0 类生产快照（建议 ≥10 万任务）上测量并记录耗时与锁表现 |

### 4.2 凭据生成与校验

```ts
import { randomBytes, createHash, timingSafeEqual } from 'crypto'

const TOKEN_PREFIX = 'ak_live_'
const TOKEN_BYTES = 32
const PREFIX_SHOW_LEN = 12          // 'ak_live_7f3c'

function generateToken(): { plain: string; hash: string; prefix: string } {
  const plain = TOKEN_PREFIX + randomBytes(TOKEN_BYTES).toString('base64url')
  return {
    plain,
    hash: createHash('sha256').update(plain).digest('hex'),
    prefix: plain.slice(0, PREFIX_SHOW_LEN),
  }
}
```

| 规则 | 说明 |
| --- | --- |
| 生成时机 | 创建代理、重置凭据 |
| 存储 | 仅 `token_hash` + `token_prefix`；明文只在响应中返回一次，随后从内存丢弃 |
| 重置语义 | 事务内 `UPDATE agents SET token_hash=$new, token_prefix=$new, updated_at=now() WHERE id=$1 AND user_id=$2`；旧值立即失效（无宽限期，PRD 4.3） |
| 校验 | `GET`/`POST` 时按 `token_hash` 命中且 `status='enabled'`；比较使用索引查找（等值），不使用明文比对 |
| 停用 | `status='disabled'` → 校验失败（4019）；执行中任务状态不受影响（PRD 4.13） |

### 4.3 状态机与不变量

```
                assign                    claim                     succeed
   none ─────────────────▶ pending ─────────────▶ running ─────────────▶ succeeded
     ▲                       │                     │   │                    │
     │  unassign             │ unassign            │   │ fail               │ unassign
     └───────────────────────┘                     │   ▼                    │
     │                                             │ failed ──retry──▶ pending
     └─────────────────────────────────────────────┘（unassign）
   delete agent:  pending → none（清空 agent_*）
                  running → agent_id = NULL（保留 running，语义"代理已删除"）
```

| 操作 | 入口 | 前置校验 | 写操作（单事务） | 失败码 |
| --- | --- | --- | --- | --- |
| 指派 | REST `POST /tasks/:id/agent`、LLM | 任务属于本人且 `status='todo'`；`task_type='normal'`；当前 `agent_state='none'`；代理属于本人且 `status='enabled'`；该代理 `pending` 队列未满 | `UPDATE tasks SET agent_id, agent_state='pending', agent_queued_at=now() WHERE id=$1 AND user_id=$2 AND agent_state='none' AND status='todo' AND task_type='normal'`；`INSERT agent_task_logs(assigned)`；提交后 `waiter.notify(agentId)` | 4021（状态/类型不允许）、4022（队列满）、1004（代理不存在/越权） |
| 更换代理 | REST（`POST` 携带新 `agent_id`，或端上"更换代理"复用同一接口 + 显式 `replace=true`） | 同指派，但允许当前状态为 `pending`/`succeeded`/`failed` | 先按"取消指派"写 `unassigned` 日志，再写新指派（同一事务） | 同上（`running` 不允许更换 → 4021） |
| 取消指派 | REST `DELETE /tasks/:id/agent`（`running` 需 `confirm=true`） | `agent_state <> 'none'`；`running` 且未确认 → 4021（端上以 4021 + `details.need_confirm=true` 呈现确认弹层） | `UPDATE tasks SET agent_id=NULL, agent_state='none', agent_queued_at=NULL, agent_claimed_at=NULL, agent_finished_at=NULL, agent_result=NULL`；`INSERT log(unassigned)` | 4021 |
| 领取 | MCP `claim_agent_task` | 任务 `agent_id = 本代理` 且 `agent_state='pending'` | `UPDATE tasks SET agent_state='running', agent_claimed_at=now() WHERE id=$1 AND agent_id=$2 AND agent_state='pending' RETURNING id`；命中则 `INSERT log(claimed)` | 4020（未命中：被抢/已取消指派） |
| 回报进度 | MCP | `agent_state='running'` 且 `agent_id=本代理` | `INSERT log(progress, content)`（不改任务状态） | 4021 |
| 回报完成 | MCP | 同上 | `UPDATE tasks SET agent_state='succeeded', agent_finished_at=now(), agent_result=$3, status='completed', completed_at=now() WHERE id=$1 AND agent_id=$2 AND agent_state='running' RETURNING id`；`INSERT log(succeeded)` | 4021 |
| 回报失败 | MCP | 同上 | `UPDATE tasks SET agent_state='failed', agent_finished_at=now(), agent_result=$3 WHERE ...`（**不改 status**）；`INSERT log(failed)` | 4021 |
| 重新执行 | REST `POST /tasks/:id/agent/retry` | `agent_state='failed'`；`agent_id` 非空（代理未删除）且代理 `enabled`；队列未满 | `UPDATE tasks SET agent_state='pending', agent_queued_at=now(), agent_claimed_at=NULL, agent_finished_at=NULL, agent_result=NULL WHERE ...`；`INSERT log(retried)`；`waiter.notify` | 4021（非失败态/代理已删除/代理停用）、4022 |
| 删除代理 | REST `DELETE /agents/:id` | 属主校验；需端上二次确认（服务端不强制 `confirm` 参数，由端上流程保证，服务端返回影响计数用于确认文案） | 事务内：`pending` 任务 → `agent_id=NULL, agent_state='none', 清队列时间` + `log(unassigned, content='代理已删除')`；`running` 任务 → `agent_id=NULL`（状态保留）+ `log` 不改；最后 `DELETE FROM agents` | 1004 |

**"指派即执行"的事务边界**：指派的三步（更新任务、写日志、计数校验）在**同一事务**内完成，`waiter.notify` 在 **COMMIT 之后**调用；若进程崩溃导致未 notify，代理侧 2s 兜底轮询仍能捞到（见 5.5）。

### 4.5 并发正确性与竞态

| 场景 | 机制 |
| --- | --- |
| 两个代理同时领取同一任务 | 条件 `UPDATE ... WHERE agent_state='pending' AND agent_id=$x`：仅一个事务能命中（行锁 + 条件重判），另一个 `rowCount=0` → 4020 |
| 同一代理重复领取同一任务 | 第二次执行时状态已 `running`，条件不满足 → 4020（**无二次状态变更**） |
| 领取与取消指派并发 | 取消指派把状态置 `none`；若代理先提交则取消指派作用于 `running`（需确认）；若取消先提交则领取 `rowCount=0` → 4020；两种顺序结果一致且无中间态 |
| 指派与删除代理并发 | 删除代理事务内先按 `agent_id` 处理队列再删行；指派事务对 `agents` 行做 `SELECT ... FOR SHARE`（或删除代理对被指派任务 `SELECT ... FOR UPDATE`）串行化；后到者因代理不存在 → 1004 |
| 入队与 waiter 唤醒竞态 | 顺序固定为"先写库提交 → 后 notify"；等待者被唤醒后**重新查库**（不依赖事件携带数据），即使 notify 丢失也有 2s 兜底轮询 |
| 回报完成与用户取消完成并发 | 回报完成用 `agent_state='running'` 守卫；用户 `complete` 走既有 `setStatus`；两者都写 `status/completed_at`，最后写入者生效，`agent_*` 不被 `setStatus` 触碰（互不覆盖） |
| 日志裁剪与并发写入 | 裁剪在写日志的同一事务内执行（`DELETE ... WHERE id NOT IN (最近 N 条)`），按 `task_id` 维度，行数有限 |

### 4.6 队列与上限

| 项 | 规则 |
| --- | --- |
| 单用户代理数 | `AGENT_MAX_PER_USER`（默认 20）；创建时 `COUNT(*)` 超限 → 4022 |
| 单代理待执行队列 | `AGENT_QUEUE_MAX`（默认 100）；指派/重试时 `countPending` 超限 → 4022，端上提示"该代理待执行任务过多" |
| 队列顺序 | `ORDER BY agent_queued_at ASC, id ASC`（先入先出） |
| 队列不过期 | 不自动过期、不自动改派（PRD 4.13）；端上展示入队时间与代理在线状态 |
| 单任务唯一排队 | `agent_state='pending'` 时该任务天然只有一行（同一 row），不产生队列重复项（I4） |

### 4.7 与 TaskService 的职责边界

| 关注点 | 归属 |
| --- | --- |
| `agent_*` 列写入 | **仅 AgentService**（TaskService 不写） |
| `status/completed_at`（代理回报完成时） | AgentService 在回报事务内直接写（一次 UPDATE，避免跨服务事务） |
| 任务标题/备注/优先级/截止时间/归属/项目 | 仅 TaskService（代理无写权限） |
| 任务删除 | TaskService 的 `remove` 删除任务行 → `agent_task_logs` 由外键 CASCADE 清理；`agent_*` 随行删除 |
| 任务完成（用户侧） | TaskService `setStatus`；不触碰 `agent_*`（执行状态与完成状态正交，I6/PRD 4.7） |
| 待办一致性 | AgentService 复用 TaskService 的 `getOwned`（统一"不存在/越权 → 404"）做任务归属校验；避免两套归属判断 |

## 5. 后端设计：MCP 接入层

### 5.1 传输与端点

| 项 | 设计 |
| --- | --- |
| 端点 | `POST /mcp`（唯一入口） |
| 协议 | MCP over Streamable HTTP（JSON-RPC 2.0），**无状态**：不返回 `Mcp-Session-Id` |
| 请求头 | `Authorization: Bearer <agent_token>`（必需）；`Content-Type: application/json`；`Accept: application/json, text/event-stream`（客户端通常都带，服务端只回 JSON）；`MCP-Protocol-Version`（后续请求携带，服务端记录并可选校验） |
| 响应 | `Content-Type: application/json`；单请求 → 单响应对象；批量（数组）→ 数组响应（保序）；通知（无 `id`）→ `202 Accepted` + 空 body |
| `GET /mcp` | 405（服务端不提供 server→client SSE 流） |
| `DELETE /mcp` | 405（无会话） |
| 超时 | 单请求最长 30s（等于 `AGENT_WAIT_TIMEOUT_MS` 25s + 余量）；长轮询工具在服务端硬上限内返回 |
| body 体积 | 复用 `express.json({ limit: '256kb' })`；MCP 请求体积小，无风险 |

> 反代要求：若前端有 nginx/网关，需保证 `/mcp` 的 `proxy_read_timeout ≥ 60s`（长轮询 25s 安全）；发布检查项见 16.2。

### 5.2 鉴权与限流

```ts
// middleware/agentAuth.ts
export const agentAuthMiddleware = asyncHandler(async (req, res, next) => {
  const token = extractBearer(req.headers.authorization)
  if (!token) return unauthorized(res)                    // HTTP 401 + WWW-Authenticate
  const hit = await agentService.resolveByToken(token)
  if (!hit) return unauthorized(res)                      // HTTP 401（4019）
  req.agent = hit                                         // { agentId, userId }
  void agentService.touchLastSeen(hit.agentId, req.reqLastSeen)   // 节流：距上次 > 60s 才写
  next()
})
```

| 项 | 规则 |
| --- | --- |
| 401 响应 | HTTP `401` + `WWW-Authenticate: Bearer realm="mcp"`，body 为 JSON-RPC 风格错误：`{"jsonrpc":"2.0","id":null,"error":{"code":-32001,"message":"代理凭据无效或已失效","data":{"biz_code":4019}}}`（协议层用 HTTP 状态，业务码放 `data.biz_code`，便于代理侧区分"凭据问题"与"业务问题"） |
| 限流 | `rateLimit({ key: 'mcp', perMin: config.rateLimit.mcpPerMin, keyOf: req => String(req.agent.agentId) })`（复用既有中间件）；超限 HTTP 429 + `data.biz_code = 1006` |
| `last_seen_at` 节流 | 内存 `Map<agentId, number>` 记录上次写入时间戳，间隔 < 60s 不写库（避免每次调用都产生写放大）；写入失败仅记 warn，不影响请求 |
| 凭据泄露面 | 401 不回显 token；错误消息不区分"token 不存在"与"代理已停用"（统一 4019 文案），避免枚举 |

### 5.5 长轮询实现（waiter）

```ts
// mcp/waiter.ts
type Waiter = { resolve: () => void; timer: NodeJS.Timeout; agentId: number }
const waiters = new Map<number, Set<Waiter>>()   // agentId → 等待者集合
let inflight = 0                                  // 全局等待者计数（并发上限）

export function notifyAgent(agentId: number): void {
  const set = waiters.get(agentId)
  if (!set) return
  for (const w of set) { clearTimeout(w.timer); w.resolve() }
  waiters.delete(agentId)                        // 唤醒后由调用方重新查库
}

export async function waitForTask(agentId: number, timeoutMs: number): Promise<AgentTaskBrief | null> {
  // 1) 先查库：已有 pending 立即返回（覆盖"唤醒丢失/跨实例"）
  const hit = await agentService.claimableHead(agentId)
  if (hit) return hit
  if (inflight >= config.agent.waitMaxConcurrency) return null   // 过载快速返回，客户端重试
  // 2) 注册等待者（含兜底轮询定时器）
  return new Promise((resolve) => {
    inflight += 1
    let done = false
    const finish = async (): Promise<void> => {
      if (done) return
      done = true
      inflight -= 1
      clearTimeout(timer)
      clearInterval(poll)
      set.delete(waiter)
      const t = await agentService.claimableHead(agentId)
      resolve(t)
    }
    const waiter: Waiter = { resolve: () => void finish(), timer: null!, agentId }
    const timer = setTimeout(() => void finish(), timeoutMs)                      // 上限 25s
    const poll = setInterval(() => { void finish() }, config.agent.waitFallbackPollMs)  // 2s 兜底
    waiter.timer = timer
    const set = waiters.get(agentId) ?? new Set<Waiter>()
    set.add(waiter); waiters.set(agentId, set)
  })
}
```

| 关注点 | 说明 |
| --- | --- |
| 唤醒路径 | AgentService 指派/重试事务提交后调用 `notifyAgent(agentId)`（同进程直接函数调用，无 IPC） |
| 兜底路径 | 2s 间隔轮询 DB（覆盖多实例部署、事件丢失、进程重启） |
| 超时 | 服务端硬上限 25s（`AGENT_WAIT_TIMEOUT_MS`）；客户端传入值被夹取到 `[0, 25000]`；超时返回 `{ task: null }`（**非错误**，客户端应立即再次调用以形成常驻闭环） |
| 过载保护 | `AGENT_WAIT_MAX_CONCURRENCY`（默认 200）达到后立即返回 null（不排队、不报错），避免连接堆积 |
| 事件循环 | 等待期间不占用 CPU、不阻塞其他请求（Promise + 定时器） |
| 内存 | waiter 随超时/唤醒立即释放；进程退出时自然丢弃 |

## 10. 前端设计：CAL-03 手势修复

### 10.1 缺陷定位（逐行）

现状（[MonthView.vue](file:///home/fy/Project/assistant/src/web/src/views/calendar/MonthView.vue#L428-L471)）：

```ts
function onShapeTouchStart(e: TouchEvent): void {
  if (animating.value) { shapeGesture = null; return }
  const list = listEl.value
  if (!list || list.scrollTop > LIST_TOP_TOLERANCE) { shapeGesture = null; return }   // 起手判定：正确
  const t = e.touches[0]
  if (!t) return
  shapeGesture = { startX: t.clientX, startY: t.clientY, lock: 'none', fired: false }
}

function onShapeTouchMove(e: TouchEvent): void {
  const g = shapeGesture
  if (!g || g.fired || animating.value) return
  ...
  if (g.lock !== 'vertical') return
  const list = listEl.value
  if (!list || list.scrollTop > LIST_TOP_TOLERANCE) return     // ← 缺陷：每帧用实时滚动位置取消判定
  if (!collapsed.value && dy <= -SHAPE_THRESHOLD_PX) { g.fired = true; void collapseCalendar() }
  else if (collapsed.value && dy >= SHAPE_THRESHOLD_PX) { g.fired = true; void expandCalendar() }
}
```

**缺陷链条**：

1. 监听为 `passive`（`@touchmove.passive`），上滑时浏览器**先**执行原生滚动，`scrollTop` 迅速 > 2px；
2. `touchmove` 中每帧重读 `scrollTop` 并作为"是否仍在列表顶部"的判据 → 一旦越界即 `return`；
3. 手指位移达到 32px 阈值前 `scrollTop` 早已 > 2px → 折叠分支**永不可达**；
4. 下拉展开方向：列表在顶部无法向上越界滚动，`scrollTop` 恒为 0 → 判定通过，故展开正常（**不对称现象的来源**）；
5. 列表内容不足一屏（不可滚动）时 `scrollTop` 恒为 0 → 折叠偶发可用（**"时好时坏"的来源**）。

### 10.2 修复方案（起手快照）

```ts
interface ShapeGesture {
  startX: number
  startY: number
  lock: 'none' | 'vertical' | 'horizontal'
  fired: boolean
  /** v0.7.0：起手快照 —— 本次手势是否从列表顶部开始 */
  startAtTop: boolean
}

function onShapeTouchStart(e: TouchEvent): void {
  if (animating.value) { shapeGesture = null; return }
  const list = listEl.value
  if (!list || list.scrollTop > LIST_TOP_TOLERANCE) { shapeGesture = null; return }
  const t = e.touches[0]
  if (!t) return
  shapeGesture = {
    startX: t.clientX,
    startY: t.clientY,
    lock: 'none',
    fired: false,
    startAtTop: true,          // 起手已在顶部（上一行已判定）
  }
}

function onShapeTouchMove(e: TouchEvent): void {
  const g = shapeGesture
  if (!g || g.fired || animating.value) return
  const t = e.touches[0]
  if (!t) return
  const dx = t.clientX - g.startX
  const dy = t.clientY - g.startY

  if (g.lock === 'none') {
    if (Math.abs(dx) < GESTURE_LOCK_PX && Math.abs(dy) < GESTURE_LOCK_PX) return
    g.lock = Math.abs(dy) > DIRECTION_RATIO * Math.abs(dx) ? 'vertical' : 'horizontal'
  }
  if (g.lock !== 'vertical') return
  if (!g.startAtTop) return                       // ← 用快照替代实时 scrollTop

  if (!collapsed.value && dy <= -SHAPE_THRESHOLD_PX) {
    g.fired = true
    void collapseCalendar()
  } else if (collapsed.value && dy >= SHAPE_THRESHOLD_PX) {
    g.fired = true
    void expandCalendar()
  }
}
```

**改动面（最小化）**

| 改动 | 说明 |
| --- | --- |
| `ShapeGesture` 接口 | 增 `startAtTop: boolean` |
| `onShapeTouchStart` | 增 `startAtTop: true`（进入该分支即已通过顶部判定） |
| `onShapeTouchMove` | 删除 `const list = listEl.value; if (!list || list.scrollTop > ...) return` 两行，替换为 `if (!g.startAtTop) return` |
| 其余 | `GESTURE_LOCK_PX` / `SHAPE_THRESHOLD_PX` / `DIRECTION_RATIO` / `SHAPE_ANIMATION_MS` / `LIST_TOP_TOLERANCE` 常量、`collapseCalendar` / `expandCalendar` / `loadCollapsed` / `loadExpanded` 与模板**均不变** |

### 10.3 边界与回归分析

| 边界 | 结果 |
| --- | --- |
| 列表可滚动 + 顶部上滑 | 触发折叠（修复目标）；触发后 `g.fired=true`，余量交还原生滚动 |
| 列表不可滚动 + 顶部上滑 | 触发折叠（与 v0.6.0 偶发可用一致，现在为确定行为） |
| 列表已滚动到中部起手上滑 | `onShapeTouchStart` 时 `scrollTop > 2` → `shapeGesture=null` → 只滚动，不触发 |
| 手势起手在顶部、但过程中列表因惯性滚动离开顶部 | 仍触发（以起手为准）；与 PRD 7.3 第 1 条一致 |
| 轻移（<8px）| 不进入方向锁，不触发 |
| 横滑（`|dy| ≤ 1.5|dx|`）| `lock='horizontal'` → 不触发；左右翻月由 `month__cal` 的独立监听处理，互不影响 |
| 折叠态下拉展开 | 行为不变（`startAtTop` 同样为 true，`dy ≥ 32` 触发） |
| 动画期间 | `animating` 门禁不变，忽略新手势 |
| 一次手势 | `fired` 保证只触发一次 |
| 未触发手势结束 | `onShapeTouchEnd` 置 `shapeGesture=null`，无状态残留 |
| 详情返回形态恢复 | `lastView.collapsed` 机制不变 |

**新增埋点**：`calendar_shape_gesture`（`dir`、`start_at_top`、`triggered`、`action`、`dy`）用于验证修复效果（T9 口径见 14.2）。

## 15. 安全设计（增量）

1. **凭据安全**：仅存 `sha256` 摘要；明文只在创建/重置响应出现一次；不进日志、不进 `tool_invocations`、不进埋点；401 不回显任何 token 片段；
2. **最小权限（I5）**：MCP 侧每个工具都以 `agent_id` 为过滤条件；越权与不存在统一 `1004` + 固定文案，无法用于探测任务存在性；
3. **写权限收口（I6）**：代理只能写 `agent_*` 与回报完成时的 `status/completed_at`；项目/日程/任务结构不可写（工具集中不存在对应工具）；
4. **鉴权隔离**：`/mcp` 只接受代理凭据；`/api/v1/*` 只接受用户 JWT；两条通道不共用中间件、不互相降级；
5. **限流与防爆破**：`/mcp` 按 `agent_id` 独立限流（默认 60/min）；连续 401 记日志（含来源 IP 类别，不记 token）；长轮询并发上限防资源耗尽；
6. **长轮询资源**：等待者随超时释放；全局并发上限 200；单请求上限 25s；不做队列排队（过载即快速返回）；
7. **注入面**：代理回报正文按纯文本存储与渲染（端上 `{{ }}` 插值，不经过 MarkdownText）；`agent_result` 长度受限（2000）；
8. **归属与级联**：`agents.user_id` 外键 CASCADE（注销账号即清代理）；`agent_task_logs.task_id` CASCADE（任务删除即清记录）；`agents` 删除走显式状态迁移，不产生"悬空执行中"脏读；
9. **不引入服务端主动出站**：MCP 为纯入站（无 webhook、无出站回调），网络攻击面只增一个受鉴权端点；
10. **审计完整性**：所有 MCP 调用落 `tool_invocations`（成功与失败），业务动作落 `agent_task_logs`，两者互为交叉验证。
